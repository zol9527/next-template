# 小程序微信登录与资料授权解耦研发执行文档

## 文档信息

- 文档日期：2026-03-16
- 适用范围：微信小程序登录、头像昵称补全、手机号授权绑定
- 负责人：待分配
- 状态：已完成开发，可继续联调与验收

## 一、背景

当前小程序登录流程以 `wx.login -> code2Session -> openid` 为主链路，后端在用户首次微信登录时会尝试结合前端传入的昵称、头像创建用户资料；当昵称缺失或不可用时，系统会自动生成类似 `wx_xxx` 的用户名。

随着微信小程序隐私能力和用户资料授权模式的变化，昵称、头像、手机号均不再适合与登录本身强耦合。继续将登录与资料补全混在一起，会导致以下问题：

- 登录流程依赖用户是否愿意授权头像昵称，稳定性不足
- 手机号并非登录必需信息，不应在首次登录时强制获取
- 微信昵称不具备全局唯一性，不适合直接承担系统唯一用户名职责
- 当前后端自动生成微信用户名，不符合产品期望

因此需要将“身份登录”和“资料授权补全”拆分为独立能力，形成更清晰、更稳定、也更符合微信授权模型的实现方案。

## 二、现状分析

### 2.1 当前后端链路

当前系统微信登录链路如下：

1. 小程序端触发 `wx.login` 获取 `code`
2. 服务端调用微信 `code2Session`
3. 微信返回 `openid`、`session_key`，部分场景返回 `unionid`
4. 服务端通过 `openid` 查找已绑定微信账号
5. 如果是新用户，则创建用户记录和微信账号绑定
6. 如果前端顺带传了 `nickname/avatarUrl`，则尝试写入用户资料
7. 如果昵称不可用，则后端自动生成 `wx_xxx` 用户名
8. 登录成功后签发访问令牌与刷新令牌

### 2.2 当前代码现状

已确认的关键实现：

- 微信登录 DTO 支持 `code`、`nickname`、`avatarUrl`
- 微信登录 Route 将资料字段透传给认证服务
- 认证服务在首次注册或资料缺失时尝试写入昵称和头像
- 认证服务对昵称唯一冲突做降级，最终生成 `wx_xxx`
- `User` 模型当前只有 `username`、`avatarUrl`、`phone`，没有独立的 `nickname` 或 `displayName`

### 2.3 当前设计问题

#### 问题 1：登录与资料补全耦合

登录只需要确定用户身份并建立会话，不应因头像昵称授权状态而影响主流程。

#### 问题 2：微信昵称不适合直接落到唯一用户名

微信昵称天然可能重复，而当前 `username` 是唯一字段。继续将微信昵称直接映射到 `username`，必然导致冲突处理复杂，最终退化为自动生成系统名。

#### 问题 3：手机号授权场景不合理

手机号通常用于下单、支付、联系人确认、售后通知等场景，不是首次登录必要条件。提前索取手机号会增加用户阻力，也与最小必要原则不符。

#### 问题 4：用户资料语义不清晰

当前缺少用于展示的“昵称/显示名”字段，导致系统内部标识与用户展示资料混用。

## 三、目标

本次改造目标如下：

1. 保持微信登录主链路稳定可用
2. 将头像、昵称授权从登录流程中解耦
3. 将手机号授权改为业务场景触发
4. 不再依赖后端自动生成微信用户名作为核心方案
5. 引入更清晰的用户资料字段模型
6. 严格遵守现有六层架构与单向依赖原则

## 四、能力边界说明

### 4.1 登录阶段可获取的数据

用户触发 `wx.login` 后，前端只能拿到：

- `code`

服务端使用 `code2Session` 后，能够稳定拿到：

- `openid`
- `session_key`
- `unionid`（非所有场景必有）

### 4.2 登录阶段不能直接获取的数据

通过 `wx.login` 和 `code2Session`，无法直接获得：

- 微信明文昵称
- 微信头像
- 手机号

因此这些信息必须走用户主动授权或主动填写流程，不能继续视为登录阶段可直接获得的数据。

## 五、总体方案

本次改造采用“一个登录主链路 + 两个资料补全链路”的方案。

### 5.1 登录主链路

职责：只负责身份识别和会话建立。

流程：

1. 小程序调用 `wx.login`
2. 前端将 `code` 提交到后端登录接口
3. 后端调用微信 `code2Session`
4. 按 `openid` 查找或创建本地用户
5. 建立本地登录会话
6. 返回当前系统登录态

### 5.2 头像昵称补全链路

职责：在用户主动配合的前提下补全展示资料。

推荐触发时机：

- 首次登录成功后的资料完善弹窗
- 用户中心资料页
- 下单前资料补全提示

### 5.3 手机号绑定链路

职责：在明确业务需要时绑定手机号。

推荐触发时机：

- 用户首次下单前
- 购买商品时需确认联系手机号
- 领取服务、课程或权益前
- 用户中心主动绑定手机号

新增或调整 DTO，全部放入 `src/contracts/dtos/wechat/` 或与用户资料相关的契约目录中。

建议新增：

#### 2. 微信资料补全 DTO

文件建议：

- `src/contracts/dtos/wechat/wechat-profile-completion.dto.ts`

请求字段：

- `nickname: string`
- `avatarUrl: string`

说明：

- `nickname` 作为展示名称，不参与唯一性约束
- `avatarUrl` 必须是合法 URL

#### 3. 微信手机号绑定 DTO

文件建议：

- `src/contracts/dtos/wechat/wechat-phone-bind.dto.ts`

请求字段：

- `code: string`

说明：

- 该 `code` 为前端触发手机号授权后返回的临时凭证
- 服务端需调用微信手机号接口换取手机号

### 6.2 接口层设计

#### 接口 1：微信登录

- 方法：`POST`
- 路径：`/api/v1/auth/wechat/login`

职责：

- 接收 `code`
- 调用认证服务进行微信登录
- 返回统一登录结果

说明：

- 第一阶段可保留旧路径或兼容旧路径
- 如果当前已有 `/api/v1/auth/wechat`，可通过兼容策略平滑迁移

#### 接口 2：微信资料补全

- 方法：`POST`
- 路径：`/api/v1/user/profile/wechat`

职责：

- 要求当前用户已登录
- 接收前端主动授权得到的昵称和头像
- 更新当前用户资料

#### 接口 3：微信手机号绑定

- 方法：`POST`
- 路径：`/api/v1/user/phone/wechat`

职责：

- 要求当前用户已登录
- 接收手机号授权返回的 `code`
- 服务端换取手机号并更新当前用户 `phone`

### 6.3 业务层设计

建议在 `src/services/auth.service.ts` 与用户资料相关服务中拆出以下能力：

#### 1. `loginWithWechatCode`

职责：

- 根据 `code2Session` 获取 `openid`
- 查找或创建用户
- 更新 `session_key`
- 返回登录结果

约束：

- 不再把资料补全作为登录成功的必要条件
- 新用户允许处于“已登录但资料未补全”的状态

#### 2. `completeWechatProfile`

职责：

- 校验当前用户登录态
- 更新当前用户展示资料

约束：

- 只更新 `nickname/avatarUrl`
- 不负责登录

#### 3. `bindWechatPhone`

职责：

- 接收手机号授权 `code`
- 调用微信服务端手机号接口
- 解出手机号后更新当前用户

约束：

- 只更新手机号绑定
- 不负责登录

### 6.4 Repository 层设计

#### UserRepository 建议新增能力

- `updateWechatDisplayProfile`
  - 参数：`userId`、`nickname`、`avatarUrl`
- `updateUserPhone`
  - 参数：`userId`、`phone`

#### WechatAccountRepository 保留能力

- `findByOpenid`
- `findByUserId`
- `createAccount`
- `updateSessionKey`

说明：

- 第一阶段保留 `session_key` 存储逻辑，避免影响现有链路
- 第二阶段可评估其是否仍有必要长期持久化

### 6.5 基础设施层设计

新增微信手机号接口封装：

- 文件建议：`src/lib/wechat/phone.ts`

职责：

- 调用微信手机号服务端接口
- 统一封装错误处理
- 统一映射微信错误码

约束：

- 严禁直接使用 `process.env`
- 必须通过 `src/config` 中已校验的环境变量访问配置
- 日志中对手机号做脱敏处理

## 七、数据模型设计

### 7.1 现状

当前 `User` 表存在以下字段：

- `username`
- `phone`
- `avatarUrl`

其中：

- `username` 唯一
- `phone` 唯一
- `avatarUrl` 可空

### 7.2 建议变更

建议为 `User` 增加独立展示名字段：

- `nickname` 或 `displayName`

推荐使用：

- `nickname`

建议约束：

- `nickname` 可空
- `nickname` 不唯一
- `username` 保留现状，但不再承担微信昵称展示职责

### 7.3 字段职责建议

#### `username`

职责：

- 系统内部唯一标识
- 后台管理或内部账号体系使用

策略：

- 新微信用户允许为空
- 不再强制从微信昵称推导

#### `nickname`

职责：

- 前台小程序展示名称
- 允许与他人重复

策略：

- 用户授权或填写后更新
- 页面展示优先读取该字段

#### `avatarUrl`

职责：

- 用户头像展示

策略：

- 用户主动授权后写入

#### `phone`

职责：

- 联系方式
- 下单、通知、售后相关业务字段

策略：

- 在明确业务节点按需绑定

## 八、时序流程

### 8.1 首次登录时序

1. 用户进入小程序
2. 前端发起 `wx.login`
3. 小程序前端拿到 `code`
4. 前端调用 `/api/v1/auth/wechat/login`
5. 接口层完成参数校验与日志上下文创建
6. Service 调用 `code2Session`
7. Repository 通过 `openid` 查找微信绑定关系
8. 若无绑定关系则创建用户和微信账号
9. Service 签发系统会话
10. 前端拿到登录成功结果
11. 前端判断资料是否完整，若不完整则展示补全提示

### 8.2 头像昵称补全时序

1. 用户点击完善资料
2. 前端通过微信头像/昵称相关交互拿到资料
3. 前端调用 `/api/v1/user/profile/wechat`
4. 接口层校验请求并确认用户已登录
5. Service 调用 `UserRepository.updateWechatDisplayProfile`
6. 返回更新成功结果

### 8.3 手机号绑定时序

1. 用户进入购买或其他需要手机号的业务流程
2. 系统判断用户未绑定手机号
3. 前端触发手机号授权
4. 前端拿到手机号授权 `code`
5. 前端调用 `/api/v1/user/phone/wechat`
6. 接口层校验请求并确认用户已登录
7. Service 调用微信手机号接口换取手机号
8. Repository 更新当前用户手机号
9. 返回绑定成功结果
10. 继续原业务流程

## 九、实施策略

本次改造建议分两阶段执行，降低对现网的影响。

### 9.1 第一阶段：兼容式改造

目标：

- 不破坏现有登录主链路
- 先把资料补全和手机号绑定能力补出来

实施内容：

1. 保留现有微信登录主入口
2. 新增微信资料补全接口
3. 新增微信手机号绑定接口
4. 新增用户 `nickname` 字段
5. 小程序接入资料补全与手机号授权新流程
6. 页面展示优先改为 `nickname ?? username ?? '微信用户'`

兼容策略：

- 登录接口继续兼容旧的 `nickname/avatarUrl` 请求体
- 但新前端流程不再依赖登录接口写资料
- 老用户和新用户同时可用

### 9.2 第二阶段：收口式改造

目标：

- 彻底收口旧设计
- 去掉登录中的资料兜底写入逻辑

实施内容：

1. 登录 DTO 最终只保留 `code`
2. 删除登录时自动生成 `wx_xxx` 用户名逻辑
3. 登录阶段不再尝试补写昵称头像
4. 完成全站展示字段清理
5. 评估是否保留 `session_key` 长期持久化逻辑

## 十三、风险与对策

### 风险 1：历史页面大量依赖 `username`

影响：

- 改造后若展示逻辑未统一，可能出现昵称不生效或空白展示

对策：

- 在前台展示层统一使用 `nickname ?? username ?? '微信用户'`
- 分阶段梳理相关页面

### 风险 2：手机号授权受微信配置限制

影响：

- 小程序主体或接口权限不足时，手机号授权可能失败

对策：

- 在开发前确认小程序后台已具备手机号相关能力
- 将失败提示设计为可恢复流程

### 风险 3：登录接口变更影响旧端

影响：

- 若直接收口 `nickname/avatarUrl`，旧端可能不兼容

对策：

- 第一阶段保留兼容入参
- 前后端逐步切流

### 风险 4：昵称字段迁移不完整

影响：

- 老用户展示逻辑不一致

对策：

- 保留回退展示逻辑
- 必要时补一轮历史数据迁移脚本
