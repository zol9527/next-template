## 一、整体流程一览

```
用户点击购买
     │
     ▼
【创建订单】→ 订单状态: 待支付 (pending_payment)
     │
     ├── 用户取消 ──────────────────────→ 已取消 (cancelled)
     │
     ├── 超时未支付（系统自动）────────→ 已取消 (cancelled)
     │
     ▼
【发起微信支付】→ 小程序拉起支付收银台
     │
     ▼
【微信回调通知】→ 系统确认收款，订单变为: 已支付 (paid)
     │
     ▼
【发放权益】→ 自动发放课程/服务权限，冻结推广佣金
     │
     ▼
【管理员确认】→ 订单变为: 已完成 (completed)，佣金解冻可结算
     │
     ├── 管理员发起退款 ─────────────→ 退款中 (refunding)
     │                                         │
     │                                         ▼
     │                                  已退款 (refunded)
     └───────────────────────────────────────────
```

## 二、第一步：用户下单

### 用户做了什么？

1. 用户在小程序商品详情页点击 **"立即购买"**
2. 系统自动创建一笔订单记录

### 系统做了什么？

| 步骤 | 说明 |
|------|------|
| ① 检查商品 | 确认商品存在且状态正常，读取当前价格 |
| ② 幂等保护 | 如果用户因网络问题重复点击，系统会识别并返回已有订单，而不是重复创建 |
| ③ 计算优惠 | 如果用户持有优惠券，自动折扣计算 |
| ④ 绑定推广码 | 如果通过推广链接进入，记录推广员关系 |
| ⑤ 生成订单号 | 格式为 `ORD + 时间戳 + 随机数` |
| ⑥ 写入数据库 | 订单状态设为 `pending_payment`（待支付） |

### 此时订单状态

```
✅ pending_payment（待支付）
```

> **注意**：订单创建后若长时间不支付，系统定时任务会自动将其取消，释放资源。

## 三、第二步：发起微信支付

### 用户做了什么？

1. 在订单列表或详情页点击 **"立即支付"**
2. 小程序自动弹出微信支付收银台

### 系统做了什么？

| 步骤 | 说明 |
|------|------|
| ① 校验订单 | 确认订单存在、属于当前用户、且状态为「待支付」 |
| ② 获取 openid | 获取用户的微信身份标识（用于支付归属认证） |
| ③ 预下单 | 向微信支付服务器发出请求，获取 `prepayId`（预支付凭证） |
| ④ 生成签名参数 | 服务端用私钥对支付参数签名，确保不被篡改 |
| ⑤ 返回给小程序 | 小程序收到参数后调用 `uni.requestPayment` 拉起收银台 |

### 用户看到的效果

- 微信支付弹窗出现，显示支付金额和商品名称
- 用户确认支付（指纹 / 密码）
- 支付成功或取消

## 四、第三步：微信回调确认

> 这一步完全在服务端自动完成，用户无需任何操作。

### 背景说明

用户在微信收银台完成支付后，**微信官方服务器**会主动通知我们的服务器「钱已到账」。这叫做「支付回调通知（Webhook）」。

### 系统做了什么？

| 步骤 | 说明 |
|------|------|
| ① 验证签名 | 用微信公钥验证通知真实性，防止伪造回调 |
| ② 解密数据 | 解密通知中加密的交易数据 |
| ③ 幂等检查 | 微信可能多次发送同一笔回调，系统识别重复并只处理一次 |
| ④ 核对金额 | 确认微信到账金额与订单金额一致 |
| ⑤ 确认支付 | 将支付记录状态更新为「成功」，记录微信交易号 |
| ⑥ 推进订单 | 订单状态从「待支付」变为 `paid`（已支付） |
| ⑦ 创建履约任务 | 自动排队等待发放用户权益 |

### 此时订单状态

```
✅ paid（已支付）
```

---

## 五、第四步：发放权益（履约）

> 「履约」指的是系统兑现对用户的承诺——给用户开通购买的课程/服务。

### 系统做了什么？

| 步骤 | 说明 |
|------|------|
| ① 定时调度 | 后台定时任务扫描待处理的履约队列 |
| ② 领取任务 | 系统用 CAS（乐观锁）确保每个任务只被处理一次 |
| ③ 发放权益 | 为用户创建课程访问权限（`course_entitlements`） |
| ④ 冻结佣金 | 为推广员创建佣金记录，状态为「冻结」（待订单完成后解冻） |

### 失败自动重试

如果发放过程中出现异常，系统会自动重试：

```
第 1 次失败 → 等待  5 秒重试
第 2 次失败 → 等待 10 秒重试
第 3 次失败 → 等待 20 秒重试
第 4 次失败 → 等待 40 秒重试
第 5 次失败 → 等待 80 秒重试（达上限 300 秒）
超过 5 次   → 标记为「需人工处理」，运营介入
```

## 六、第五步：管理员确认完成

### 管理员做了什么？

在管理后台，确认用户权益已正常发放，点击「确认完成」。

### 系统做了什么？

| 步骤 | 说明 |
|------|------|
| ① 校验状态 | 确认订单为「已支付」状态 |
| ② 更新订单 | 状态从 `paid` → `completed`，记录完成时间 |
| ③ 解冻佣金 | 推广员佣金从「冻结」变为「可结算」，进入结算流程 |

### 此时订单状态

```
✅ completed（已完成）
```

## 七、退款流程

> 退款由**管理员**在后台发起，目前系统支持全额退款和部分退款。

### 7.1 退款前置条件

| 条件 | 说明 |
|------|------|
| 订单状态 | 必须是 `paid`（已支付）或 `completed`（已完成） |
| 退款金额 | 不能超过用户实际支付金额 |
| 佣金状态 | 推广佣金不能处于「结算中」或「已结算」状态（否则不可退） |

### 7.2 退款步骤

```
管理员点击退款
     │
     ▼
① 系统校验订单状态与金额合法性
     │
     ▼
② 检查佣金是否可退（未进入结算流程）
     │
     ▼
③ 调用微信退款 API（幂等保护：重复调用不会重复退款）
     │
     ▼
④ 更新订单退款金额
     │
     ├── 全额退款 → 状态: refunded（已退款）
     │
     └── 部分退款 → 状态: refunding（退款中，可继续追加退款）
     │
     ▼
⑤ 调整推广佣金（按比例扣减）
```

### 7.3 退款到账时间

根据微信支付官方政策，退款金额将原路返回用户支付账户：

- **一般情况**：1~3 个工作日内到账
- **节假日**：可能延迟

### 7.4 退款幂等保护

系统通过幂等键保护退款接口，即使管理员因网络原因多次点击，**微信也只会执行一次退款**，不会重复退，保证资金安全。

## 八、订单状态速查表

| 状态值 | 中文名 | 含义 | 用户可见？ |
|--------|--------|------|-----------|
| `pending_payment` | 待支付 | 订单已创建，等待用户付款 | ✅ 是 |
| `paid` | 已支付 | 微信已确认收款，权益处理中 | ✅ 是 |
| `completed` | 已完成 | 权益发放完毕，管理员已确认 | ✅ 是 |
| `cancelled` | 已取消 | 用户取消或超时自动取消 | ✅ 是 |
| `refunding` | 退款中 | 部分退款进行中 | ✅ 是 |
| `refunded` | 已退款 | 全额退款完成 | ✅ 是 |

## 九、常见问题 FAQ

**Q：用户支付完成，但订单还显示「待支付」？**

> A：这通常是微信回调延迟，一般几秒内会自动更新。若超过 5 分钟仍未更新，请查看日志中的回调记录，检查验签是否通过。

---

**Q：用户重复点击「购买」会下多个订单吗？**

> A：不会。系统有幂等保护机制，24 小时内相同用户对相同商品的重复请求会返回已有订单。

---

**Q：退款失败怎么办？**

> A：系统会记录退款失败原因，管理员可在后台查看。常见原因包括：微信退款 API 超时、余额不足等。可重新发起退款（幂等保护确保不重复）。

---

**Q：推广员的佣金什么时候到账？**

> A：用户下单支付后佣金进入「冻结」状态；管理员确认订单完成后，佣金变为「可结算」，进入结算队列。**如发生退款，佣金会按比例扣减。**

---

**Q：履约失败（权益没发出去）怎么处理？**

> A：系统会自动重试最多 5 次。若全部失败，任务会标记为「需人工处理」，运营人员需手动在后台介入处理，并通知用户。
